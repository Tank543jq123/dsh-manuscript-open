# 书阁 · dsh-manuscript

> **把过去几百次 AI 对话，编译成一本有目录、能查阅、可溯源的手册。**
>
> 零外部服务、零 API key —— 目录、归册、检索、溯源全在本机完成。
> 检索以关键词为主；**向量召回是可选的本地增强**（放一个 GGUF 才启用，不装照样能用），
> LLM 提炼是另一条可选增强轨，不是前置依赖。
>
> **数据边界（必读）**：T1 会把 digest（标题/项目/事件片段）发到配置的 LLM；条目以**明文**存库目录（**无加密**）。
> `DSH_MANUSCRIPT_T1=0` 可完全禁用 T1；敏感会话不建议跑 T1。公开版不附内部工作区截图。
>
> **公开版不含真实工作区截图**：截图会暴露内部项目名、工作区名与路径。下面用文字、ASCII 流程和 Mermaid 结构图说明。

```mermaid
flowchart LR
  A[左栏迷你卡] --> B[书房面板]
  B --> C[册 → 章 → 条目]
  C --> D[manual_toc / manual_read]
  D --> E[回答 + 出处]
```

## 它解决什么问题

你和 AI 助手聊过几百次。里面有很多真东西：某个插件为什么装不上、某块板子的选型取舍、某次排查是怎么走通的。

但这些东西**都在聊天记录里，散落、无序、翻不到**。下次遇到同样的问题，你还是得从头问一遍 —— 因为你不记得"三个月前那次我是怎么解决的"。

更糟的是：AI 自己也不记得。每次新对话都是零上下文，它会：
- 用同样的方式再踩一次同样的坑
- 或者更糟：**编一个听起来很合理的答案**，而你不知道那是编的

**书阁做的事**：把这些对话里**真实发生过**的东西提炼出来，编成一本手册。下次开新对话，AI 先翻这本手册，发现自己记过这件事 —— 就照实说，而不是编。

## 三个关键设计

### ① 结构不交给向量，用手册的结构

主流的"记忆"方案都是向量检索：切片、嵌入、相似度匹配。问题是**你没法审查它**——为什么检索到这条？不知道。它记错了什么？不知道。

书阁用最笨也最可查的办法：**册 → 章 → 条目**，三级目录，全是人能读的明文。

```
册（VOL.03 DSH 插件开发）
 └── 章（插件安装与升级）
      └── 条目（「重复键会让 cordis 插件进入启动崩溃循环」）
           ├── claim：发生了什么、为什么、怎么修
           ├── 证据：用了哪些工具、改过哪些文件
           └── 溯源：来自哪个会话、什么时候
```

翻开就是目录，点进去就是原文，每条都能追回原始对话。

> **向量只做检索的补充，不做结构的替代（2026-11-12）**：
> 把本地 embedding 权重（GGUF）放进 `<库根>/models/`，检索会多一路向量召回 ——
> 关键词 + 语义两路做 RRF 融合，**纯语义项永远排在关键词命中之后**，
> 且必须过绝对余弦阈值（默认 0.62），过不了就返回 0 条（不硬编）。
> 没有权重、没有 llama.cpp、嵌入失败 —— 任意一种情况都静默退回关键词 + 词频两路，
> `manual_recall` 不会因此报错。索引落在 `<库根>/vectors.json`，按条目内容 hash 增量重建。

### ② 数字必须能溯源

这是最容易被忽略、也最致命的一点：**AI 编数字**。

"这个插件失败率大概 30%" —— 30% 是哪来的？如果手册里没有这个数，那就是编的。

书阁的做法很硬：提炼出的每一条，**里面出现的每个数字都必须在原始会话摘要里找得到**。找不到就丢掉那一条。

> 实测代价与收益：新模型源 23 轮提炼里，有 3 轮因为模型写了个「30」（"约 30 秒"）而被拦下。那些会话的摘要里确实没有 30 —— 拦对了。代价是每轮 5 个会话白跑，所以后来改成"只丢那一条，不整批作废"。

### ③ 永不删除

手册里的条目**只增不减**。更新只走两条路：
- 新的同类经验 → 作为新条目加进来
- 冲突 → 两份都留，标记出来让人判断

为什么这么固执：一条经验可能是三个月前那次排查唯一的记录。程序判断"这条重复了"而删掉它，代价是不可逆的。

## 界面

### 目录：按册分，一册一卷

本机实测有内容的 **6 个册**：硬件设计与器件选型、DSH 插件开发、AI 协作方法与踩坑、本地模型与推理环境、网页抓取与检索、未分类收件箱。

> 另有 3 个册（嵌入式固件、EDA 与 PCB、系统与运维）**已经在册表里定义但当前为空** —— 你的语料里还没有这几类的会话。空册不进面板，等有内容才出现。

**册是自动归的**（信号加权：项目名 + 工具指纹 + 关键词），但**宁可放进收件箱，也不归错册** —— 归错比不归更难发现。

### 条目长什么样

每条形如：

```markdown
### 重复键会让 cordis 插件进入启动崩溃循环

在 cordis.patch.yml 里给同一个插件配置两次同名键（旧值一行、新值一行），
YAML 严格解析直接报错，插件进入启动崩溃循环，手动重启也无法恢复。

证据：工具 write / bash · 文件 cordis.patch.yml
来源：session-49ba25cf（2026-10-20）
```

**claim** 是自包含的结论（不看原文也能懂），**证据**是确定性的"干了什么"，**来源**能追回原始会话。

## 它是怎么工作的

```
DSH 会话目录（~/.dsh/sessions/…）
        │
        │  ① 扫描：解压 zstd、解析 JSONL、抽特征
        ▼
   分诊（零 LLM，纯规则）
        │  真实任务 / 冒烟 / 空壳 / 噪声
        │  质量分、交付物数、工具调用数
        ▼
   ┌────┴────┐
   │         │
   ▼         ▼
 T0 骨架    T1 提炼（可选）
 确定性     LLM 生成
   │         │  ② 数字溯源 → ③ 自动裁决 → ④ 去重
   │         ▼
   └────┬────┘
        ▼
   归册（信号加权）+ 主题章
        │
        ▼
   entries/*.json  ← 真相层
   volumes/*/MANUAL.md + TOC.md
   library.json    ← 投影（可从上面重算）
        │
        │  ⑤ 三层注入
        ▼
   下次对话时，AI 自动看到目录 + 命中的条目
```

### 三层注入：AI 怎么"翻到"手册

| 层 | 时机 | 内容 |
|:---|:---|:---|
| **L1** 系统提示词 | 每次对话 | 契约 + 目录（册/章/条目数），有行数与字节上限 |
| **L2** 首轮预取 | 收到第一条消息 | 按关键词/工具名召回相关条目，附在上下文里 |
| **L3** 七个工具 | AI 主动调用 | `manual_toc` / `manual_read` / `manual_recall` / `manual_trace` / `manual_distill` / `manual_mount` / `manual_unmount` |

AI 不是"被告知有一本手册"，而是**在上下文里就能看到目录和命中的条目**。想深挖再调工具。

## 快速开始

> ⚠️ **它是 DSH 插件，不是独立程序** —— 必须装在 DeepSeek Harness 里才能运行。

### 装三步

```bash
# 1. 把插件放进 profile 的 node_modules
ln -s /path/to/dsh-manuscript ~/.dsh/profiles/<profile>/node_modules/dsh-manuscript

# 2. 让 profile 引用它（在 profile 的 package.json 里）
#    "dsh": { "profile": { "bundles": [ ..., "dsh-manuscript" ] } }

# 3. 重启 DSH —— 是重启，不是刷新页面
```

### 装之前就能自检

```bash
node scripts/test-toolpacks.mjs      # 13 项
node scripts/test-distill-state.mjs  # 41 项
node scripts/selfcheck.mjs           # 23 项（只读会话；建库落临时根）
```

### 一把跑完全部测试

```bash
node scripts/test-all.mjs   # 32 份脚本 / 1093 项断言 / 约 25 秒
```

### 每日巡检

```bash
node scripts/daily-check.mjs            # 线上巡检：正向（必须命中指定条目）/ 负控 / 全量测试，并推送摘要
node scripts/daily-check.mjs --dry-run  # 只打印，不推送、不写日志、不跑测试
```

`manuscript-daily-check.timer` 每天 07:00 自动跑一次；失败时摘要以「❌」开头并写明缺哪项，推送桥不可用时退出码非 0。
`scripts/patrol.mjs` 是**手动排查**用的离线版（只读 `library.json`，直接调 `matchEntries`，不依赖 HTTP 服务）。

## 验收：手册真的有用吗

装好之后，最有说服力的验证是这一句：

> **新开一个会话，问它："你手册里关于 XX 记了什么？只回答手册里的内容。"**

实测结果（公开版不附内部工作区截图）：

- Agent **没有调用任何工具**就报出了 VOL.01 的条目
- 报的内容包括：规模（1 轮 · 252 次工具调用 · 1 个交付物）、证据（工具 bash/web_fetch/web_search，文件两个）、质量口径（speculation · L3）
- 然后它说：**「手册只记了哪次会话、用了哪些工具，没有选型结论 —— 我不会拿训练知识替它补一个"手册说过的结论"。」**

最后那句是关键。**手册的价值不只是"记住了什么"，也是"明确知道自己没记什么"。**

## 入口边界（必读）

书阁是 **DSH 手册插件（host + client）**，自己不监听 GitHub/飞书/微信，也没有独立 HTTP 服务。
它通过 DSH 面板、`manual_*` 工具和对话被使用。

GitHub / 飞书 / 微信 / 本地命令 / HTTP 是 **SuperAgent 编排层的入口**，不是书阁插件自身的能力；
如果你同时装了 SuperAgent，可以用那些信道派活，但不要把“五入口”算作书阁的卖点。

## 四条红线

| | 红线 | 怎么做到的 |
|:---|:---|:---|
| ① | **永不自动删除** | 条目只追加；冲突保留两份 |
| ② | **数字必须可溯源** | 每个数字都要在原始摘要里找得到，否则丢掉那一条 |
| ③ | **不静默失败** | 坏条目计数、扫描错误明细、跳过原因全部透出 |
| ④ | **写明它不知道什么** | 缺上下文时如实说"手册无记录"，不用训练知识补 |

## 已知局限

诚实列出，不是待办清单的美化版：

1. **UI 只在真实宿主渲染过三次**（2026-11-08 首次、11-09 两次），且都是抽查指定页面，不是全量点击验收
2. **276 条条目没有逐条人工评估** —— "有没有用"程序判断不了，只有抽样看过十几条
3. **Windows 完全未验证** —— 平台分支已写出但标注为"未验证方案"
4. **提炼依赖模型守格式** —— 模型偶尔会写散文而不是 JSON，重试一次仍失败就丢掉那批
5. **历史条目的归册不会自动修正** —— 新增册只对未来入册生效（`volume` 入册时写死，尊重"只追加"）
