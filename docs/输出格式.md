# 书阁的输出格式（给"图书馆"用的契约）

> 目的：说清楚 `~/.dsh/dsh-manuscript/` 里到底有什么、哪些是**真相**、哪些是**投影**、
> 跨设备同步时该拿哪些、不能拿哪些。
> 依据：2026-11-08 在本机 130 个真实会话上建库实测（104 条目 / 4 册 / 628 KB）。
> 文中所有数字都是当次实测值，不是承诺。

---

## 一、一句话

**输出全是纯文本：89 个 JSON 条目 + 每册两个 Markdown + 一份总账 JSON + 建库凭证。**
没有数据库、没有索引文件、没有二进制，`git` 直接能管。

---

## 二、目录树与体积（实测）

```
~/.dsh/dsh-manuscript/
├── library.json            120 KB  ← 总账（**投影**，见 §四）
├── entries/                 94 KB  ← 104 个 .json，平均 ~900 B/条（**真相**）
│   └── e-d9e4ba5d239c.json
├── volumes/                        ← 每册两个 .md（**人读的成品**）
│   ├── vol-01/{MANUAL.md, TOC.md}
│   ├── vol-03/{MANUAL.md, TOC.md}
│   ├── vol-07/{MANUAL.md, TOC.md}
│   └── vol-05/{MANUAL.md, TOC.md}
├── runs/                    ← 每次建库/提炼的凭证（设备本地，见 §五）
│   └── run-20261108-104605-7aef6e.json
├── archive/                 ← 预留，当前为空
└── snapshots/               ← 预留，当前为空
```

总量级：**100 条约 0.6 MB；1000 条约 6 MB**。纯文本，压得动、diff 得动。

## 三、单个条目（`entries/<id>.json`）

这是整套系统的原子单位，也是"图书馆"唯一真正需要同步的东西。

```json
{
  "id": "e-d9e4ba5d239c",
  "volume": "vol-05",
  "chapter": "ch-scrape",
  "chapterTitle": "网页抓取与检索",
  "title": "领英求职人信息抓取可行性",
  "sessionAt": "2026-10-18T11:51:37.555Z",
  "claim": "25 轮 · 305 次工具调用 · 9 个交付物 · （多轮讨论）",
  "why": "",
  "confidence": "speculation",
  "authority": "L3",
  "status": "current",
  "needsReview": true,
  "assignReason": "无任何信号命中 → 收件箱",
  "qualityScore": 8.98,
  "provenance": {
    "session_id": "session-1d544d46-28fd-437f-a93d-fded4d4dea08",
    "turn": null, "message_id": null, "tool_call_id": null,
    "timestamp": "2026-10-18T11:51:37.555Z"
  },
  "tags": ["HR信息收集"],
  "evidence": {
    "tools": ["bash", "read_image", "edit"],
    "files": ["领英供需数据挖掘-SOP.html", "领英求职者抓取-可行性汇报.html"]
  },
  "hits": 0,
  "last_hit": null,
  "slot": 47
}
```

字段语义（跨设备同步时**必须**保住这些）：

| 字段 | 作用 | 能不能改 |
|:---|:---|:---|
| `id` | `sha256(session_id)[:12]`，`e-` 前缀 | **不能**。它是全局主键，见 §六 |
| `volume` / `chapter` / `chapterTitle` | 归册与归章 | 能（人工重归类是合法操作） |
| `title` | 一句话结论的标题 | 能（人工改写是合法操作） |
| `claim` | 结论正文（T0 是统计骨架，T1 是 LLM 提炼） | 能 |
| `why` | 为什么这么归/这么判 | 能，允许空 |
| `confidence` | `stated`/`high`/`medium`/`speculation`（**字符串**，不是数字） | 能 |
| `authority` | 来源等级：`L1` 人写 / `L2` LLM 参与 / `L3` 规则骨架 | 能 |
| `status` | `current` / `expired`（过期只标记、**永不删除**） | 能 |
| `provenance` | 出处（session_id + 时间；T1 还有 session_ids / source_kind） | **不能**改，改了溯源就废了 |
| `evidence` | 确定性线索：用过哪些工具、写过哪些文件（只有 basename） | 可空 |

## 四、`library.json` 是投影，不是真相

```json
{
  "version": 1,
  "generatedAt": "...",
  "counts": { "total": 130, "real": 104, "entries": 104, ... },
  "stages": { "counts": {...}, "byStage": {...}, "exhaustive": true },
  "byVolume": { "vol-03": 46, "vol-05": 47, ... },
  "volumeFallbacks": [], "volumeNormalized": [],
  "volumes": [ { "id": "vol-03", "chapterList": [ { "slug": "ch-plugin", "entries": [ ...完整条目... ] } ] } ]
}
```

三个要点：

1. **它把每个条目又在 `volumes[].chapterList[].entries[]` 里内联了一遍** —— 120 KB 里大半是这份重复。
2. 每次建库由磁盘上的 `entries/` **重新生成**，`counts` 以磁盘实数回写。
3. 因此：**它是派生品**。多设备场景下同步它没有收益，反而会互相覆盖。

> 结论：**别同步 `library.json`**。每个设备本地重建，内容自然一致。

## 五、册的 Markdown（人读的成品）

`volumes/<册>/MANUAL.md` 是"说明书"形态：`# VOL.xx 册名` → 目录（锚点链接）→ 每章 `## 章名` → 每条 `### 标题 / claim / <sub>置信度·权威·命中</sub>`。
`TOC.md` 是纯目录（章 + 前 5 条标题 + "另有 N 条"）。

**这两份是给人和 `grep` 看的**，落盘时由 `entries/` 生成，不承载额外信息。
如果图书馆要自己做渲染，可以完全忽略它们；如果只想给人翻，直接读它们最省事。

⚠️ 已知缺口：`MANUAL.md` **还没有渲染 `evidence`**（工具/文件名只出现在 `manual_read` 工具输出里）。想让 Markdown 也带上，是一处小改动。

## 六、跨设备合并：现在能做什么、还缺什么

### 已经成立的（实测）

| 事项 | 结论 |
|:---|:---|
| 主键冲突 | 不会。`id = sha256(session_id)[:12]`，session id 是 UUID，两台设备不可能撞 |
| 另一台设备的条目会不会被本机重建删掉 | **不会**。实测：写入一条"本机没有对应会话"的条目后重建，`created=0 kept=104`，`counts.entries` 从 104 → 105，文件仍在 |
| 能不能用 git 同步 | 能。全是文本，冲突也只在同一文件 |
| 内容是二进制吗 | 不是。JSON + Markdown，UTF-8 |

### 已经补上的（2026-11-08）

1. **设备标识 `origin.device`** ✅
   条目在**入库时**写入 `origin: { device: "..." }`。取值的优先级：
   `DSH_MANUSCRIPT_DEVICE` 环境变量 → 主机名 → `unknown-device`（裁到 64 字符）。
   默认用主机名是为了零配置、可读；两台机器同名时显式设环境变量即可。
   注意：它记录的是**产出这条条目的设备**，不是"最后修改它的设备"。

2. **`createdAt` / `updatedAt`** ✅
   建库派生与入册写入时都会带上这两个 ISO 时间戳。
   注意它的语义边界：**入册是只追加**。同 id、不同内容不会覆盖旧条目，而是生成
   `-2` 后缀的新条目（见 commit.js 的 uniqueId）。所以 `updatedAt` 记的是
   "这条被写入的时间"，不是编辑历史；要**改**已有条目，得走同步层的更新路径
   （尚未实现，见下方"还缺的"）。

3. **`runs/` 是设备本地的** ✅（结论不变，写进文档）
   它是"这台机器某次建库/提炼的凭证"，跨设备合并没有意义（文件名含时间+随机数），
   建议不同步，或按 `<device>/` 分目录。

4. **`volumes/` 是投影** ✅（结论不变）
   同 `library.json`：可重建，不必同步（除了想直接读 md 的场景）。

### 冲突策略：已有可跑的工具（2026-11-08）

`scripts/merge-libraries.mjs` + `lib/merge.js`。规则如下（都写进了测试）：

| 情形 | 处理 |
|:---|:---|
| 只在一边有 | **新增**（不丢） |
| 两边内容一致 | **跳过**（不重复写；判等只看内容字段，不看 `updatedAt`/`hits`） |
| 内容不同、`updatedAt` 可比 | **新的赢**；旧的那份**另存为冲突副本** |
| `updatedAt` 相同或缺失 | **不猜**：目标侧原件保持不动，对方那份进 `conflicts/` |
| 任何情况 | **不删除任何条目** |

```bash
# 先看计划（默认 dry-run，不写盘）
node scripts/merge-libraries.mjs --base ~/.dsh/dsh-manuscript --incoming /mnt/usb/device-b

# 真写（新增/更新 + 冲突留档到 <base>/conflicts/）
node scripts/merge-libraries.mjs --base ~/.dsh/dsh-manuscript --incoming /mnt/usb/device-b --apply
```

为什么规则 3 也要留副本：`updatedAt` 只证明"谁后写"，证明不了"谁是对的"。
副本几 KB，丢一条经验是不可逆的。

合并后不需要手工改 `library.json` —— 它是投影，下一次正常建库会自动重算。

### 还缺的

1. **`MANUAL.md` 已渲染 `evidence`** ✅（2026-11-08）
2. 还没有"条目更新路径"（入册是只追加；要改已有条目得走同步层，目前需手工改 JSON）。

### 推荐的最小同步集

```
entries/*.json      ← 唯一必须同步的（真相）
origin.device       ← 已补，用于多设备视图
library.json        ← 不同步，本地重建
volumes/*.md        ← 不同步（可重建），除非有设备只想读文本
runs/*.json         ← 不同步
```

合并流程（推荐）：

```
拉取 → 解冲突（字段级）→ 本地重建 library.json + volumes/*.md → 推回 entries/
```

## 七、如果"图书馆"要另存一套格式

现有真相层已经很"可搬"：每条是一个自包含 JSON，`title/claim/provenance` 都在里面。
如果图书馆要自己的 schema，建议：

- **保留 `id` 与 `provenance` 原样**（换成别的 id 就再也对不回会话）
- **保留 `status`、`confidence`、`authority`**（它们决定"这条能不能当依据"）
- `volume/chapter` 可以映射成图书馆自己的分类，但建议留一个 `originVolume` 备查
- 不要试图解析 `claim` 的格式 —— T0 是统计串、T1 是自然语言结论，形状不同是**设计如此**（见 README 的"真相层"一节）
