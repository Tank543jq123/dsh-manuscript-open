# 项目目标 · 书阁 dsh-manuscript

> 本文回答三个问题：**这东西到底解决什么问题、做到什么算成功、什么不做。**
> 它是判断"某个功能该不该加"的依据，也是接手开发时对齐目标的第一份材料。
> 最后更新：2026-11-07（第 3 版，含接手实测后的现状校准）

---

## 一、一句话

**把 DSH 里已经归档的对话，编译成一本有目录、可溯源的手册；让 Agent 开工前先翻目录，而不是把历史塞进提示词。**

---

## 二、要解决的问题

### 2.1 现状的痛

一个长期在用 DSH 的人，会话库里躺着几百个会话：查过的料、踩过的坑、定过的方案，全在里面。
但这些内容对下一次开工几乎是**不可用**的：

| 做法 | 为什么不行 |
|:---|:---|
| 全部塞进系统提示词 | 几百个会话是几十 MB，塞不进去，塞进去也会把上下文挤爆 |
| 靠 RAG / 向量检索 | 引入 embedding 模型与向量库，多一层依赖、多一份不透明；而且"向量相似"不等于"这条经验成立" |
| 靠模型自己记住 | 模型不知道你的项目、你的器件、你上周定过的那个方案 |
| 翻文件 / 翻聊天记录 | 人肉成本高，翻完也说不清"这条是哪次会话、哪个结论" |

结果是：**每次开工都从零讲一遍背景**，上一次的结论没有沉淀，同一个坑重复踩。

### 2.2 本项目的主张

把"记忆"从一次**检索问题**，改造成一次**出版行为**：

- 会话 → 提炼成**条目**（一条结论 + 出处）
- 条目 → 按主题归入**册 → 章**
- 册与章 → 生成**目录**
- 每次开工，Agent 先看目录（几百字），需要细节时再按需读正文（几 KB）

**关键判断：目录可以很小，正文可以很大，但目录必须好到"看目录就知道该不该翻"。**

## 三、目标用户与场景

| 用户 | 场景 |
|:---|:---|
| 长期用 DSH 干同一类活的人（硬件 / 固件 / 插件开发） | 换电脑、隔两周回来、"上次那个电源方案是怎么定的" |
| 需要把经验交付出去的人 | 新人接手、写交接文档、把踩坑沉淀成团队资产 |
| Agent 本身 | 每一轮开工前，用目录判断"这件事手册里记没记过"，记过就先读正文 |

## 四、四条设计承诺（不可动摇）

这四条是产品定义，不是实现偏好。任何改动如果破坏其中一条，就不该合。

1. **目录即索引**
   不用 embedding，用册名 / 章名 / 条目标题。目录常驻、体积有硬上限；正文按需取。
   → 判据：目录注入 ≤ 200 行 / 25 KB；超限必须**拒绝注入**并显式报 `overflow`，不许砍一半装成功。

2. **出处即信任**
   每条经验都要能回答"你凭什么这么说"：哪个会话、什么时候、哪条消息。
   → 判据：条目带 `provenance`；查不到出处的不得入册（**当前是纪律要求，尚未代码强制，见 §7**）。

3. **书是长出来的**
   每次提炼长一段枝；被取代的条目不删除，只标 `expired`（界面上是虚线）。
   → 判据：全库没有删除条目/删除册的代码路径。

4. **进度即承诺**
   漏斗的每一段都能点开，看得见"卡在哪、卡了多久"。数字必须带出处，拿不到就说拿不到（返回 `null`，不填 `0`）。

## 五、明确的非目标

写清楚"不做"，是为了避免它长成一个什么都想干的怪物：

- **不替代 AGENTS.md / 系统提示词。** 规矩留在正文，手册只放目录与经验索引。
- **不做向量检索、不依赖外部服务。** `dependencies` 保持为空对象；没有网络、没有密钥时，目录、归册、查阅、溯源必须全部可用。
- **不改 DSH 本体。** 只是插件：host 侧注册 prompt section / 工具 / HTTP 路由，client 侧挂四个 UI 槽位。
- **不自动删除任何东西。** 过期只标记；唯一允许删的是超 1 小时的 `.staging-*` 临时残留。
- **不做云同步。** 真相层是纯文本 + JSON，用 git 自己同步即可（这也是它坚持"人可读、可 diff"的原因）。
- **不做通用知识库。** 只处理"本机会话库里真实发生过的事"，不抓网页、不灌外部语料。

## 六、成功的判据

不写"好用""智能"这种没法验收的话。可验收的只有这几条：

| # | 判据 | 怎么验 |
|:--|:---|:---|
| S1 | 换一台机器、只给会话库，能一条命令建出完整的册/章/条目结构 | `node scripts/selfcheck.mjs`（需先让它可移植，见 §7） |
| S2 | Agent 拿到目录后，**能判断"该不该翻"**：问手册里有的东西，它会先读正文；问没有的，它明说"手册无记录" | 新开会话提一个手册里记过的问题，看首轮是否说"我看到手册里记过…" |
| S3 | 手册里的每条经验都能反查回原始会话 | `manual_trace(entry_id)` |
| S4 | 任何一次写入都可解释、可回滚：只追加、有凭证、有锁 | 重建两次 `created=0`；`runs/` 有对应凭证 |
| S5 | 出问题时**不会静默**：截断有 `clamped`、超限有 `overflow`、快照旧有 `stale`、占锁有 `409` | 黑盒打接口，逐条看状态码与字段 |

> 注意 S2 是唯一"没有它就等于没做成"的判据。目录再好，Agent 不用，这个项目就只是个静态站点。

## 七、当前现状（2026-11-07 实测，诚实版）

**架构已完成，产品效果未达标。** 分开说：

### 已经站得住的部分

- 两条轨的骨架完整：**T0 确定性轨**（扫描 → 分诊 → 归册 → 原子落盘，零 LLM、零向量）与 **T1 LLM 增强轨**（编排 → 提炼 → 裁决 → 入册），且都只能通过 `commit.js` 这一个写盘口。
- 工程安全做得比同类项目扎实：暂存区 + 原子写 + 建库锁 + TTL + pid 存活检测；只追加、不覆盖、不删孤儿；重建保人工修改。
- 接口语义干净：写操作三重守门（Host 回环 → Origin 同源 → 守门头），405/400/413/409/404 各有其义，3 MB body 回 `413` 而不是断连。
- 自带 19 个零写盘测试脚本、624 项断言；HTTP 黑盒 74 项。

### 还没有兑现的部分（决定了下一步优先级）

1. **条目没有"经验"，只有统计。** T0 产出的 100% 的 claim 是 `N 轮 · M 次工具调用 · K 个交付物`——没有 LLM 时，"手册"等于会话标题列表。**这是与 §2.2 差距最大的一处。**
2. **检索对中文短查询失效。** 匹配要求命中 ≥3 个 bigram，而 2–3 字查询最多只能产生 1–2 个 → 数学上不可能命中，L2 首轮预取因此零触发（S2 直接判负）。
3. **"章"目前是项目目录名，不是主题。** 一个 `default workspace` 章吃掉半数条目，目录因此失去索引价值（§4.1 只剩形式）。
4. **入册口不设防。** `commit` 不校验字段、无幂等，能写出空 id 条目、重复入册（§4.2 的代码强制尚未落地）。
5. **归册规则硬编码作者本机项目名**，换机器后多数条目落收件箱；两册因 `data/` 不入库而永远是空的。

> 这些不是"优化项"，是**目标未达成的证据**。修它们的顺序见 `docs/开发计划.md`（随修复计划一起提交）。

## 八、边界与风险（已知并接受）

- **规模**：全量扫描是 O(会话数)，当前上百会话约 2 秒；上千会话需要增量扫描。
- **匹配质量**：用 bigram 而不是真分词，是刻意的"零依赖"取舍，召回天然不如分词。它必须"宁缺勿滥"（查不到就说没有），但**不能"必然查不到"**——那是当前缺陷，不是取舍。
- **LLM 提炼不可信**：模型会编数字。所以提炼只产 proposal、数字要溯源、裁决要机械可复核、入册要人工确认。
- **只在 Windows + DSH 0.2.1-rc.2 实测过**（接手后在 Linux + 0.2.1-rc.5 复验了 T0 轨）。跨平台仍是风险点。

## 九、这个项目做成了是什么样

> 一个人换到新电脑，装上 DSH，插件指向旧的会话库。
> 三秒后左栏出现 `📖 书阁 267/304`。
> 他问 Agent："上次那颗隔离电源最后选的是哪颗？"
> Agent 说："我先翻一下手册。" —— 然后引用了一条带出处（会话 + 时间）的结论，
> 并说清"这条是 10 月 21 日那次选的，当时理由是纹波；这次条件不同的话需要重新评估"。
>
> **不炫技、不假装记得、不编。目录小、凭证全、能反查。**

这就是验收线。
